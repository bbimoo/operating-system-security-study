### 0. 강의 도입: PHP 사례와 중간고사 범위

#### PHP 취약점

- 원인? - **Remote Code Execution (RCE)** : 원격으로 코드를 실행할 수 있는 취약점.
- 두 개의 단계, 왜 일어났는지
  1. 메모리를 과하게 요청하면 오류가 나고, 오류가 나면서 메모리를 해제함. 이때 초기화를 하지 않음.
  2. 프리된 걸 다시 쓰겠다는 취약점이 다시 발생하면 이전에 초기화되지 않은 내용을 가지고 조작함. 그래서 취약점이 발생.
- 과제물과 관계 : 오류가 나면 메모리를 해제하는데 초기화를 하지 않고 해제하여 정보가 남아 있음 → **Object Reuse Protection**

#### 셸 코드를 스택에 주입해서 실행하는 공격의 방어 기법

| 방어 기법 | 설명 |
|---|---|
| 1. 스택 카나리 | |
| 2. NX 비트 | 우회하는 방법이 나옴. ASLR이나 대시 셸도 우회하는 방법이 나왔다는 것을 이전에 배움. |

**NX 비트란?**

- 어떤 특정한 페이지나 세그먼트(스택)에 주입된 코드가 실행되지 않으면 좋겠다.
- NX 비트가 ON으로 되어 있으면 셸 코드가 주입되더라도 해당하는 세그먼트가 실행되지 않는 영역으로 바뀜.
- 주로 코드를 주입할 수 있는 영역은 쓰기가 발생하는 영역. 일반적으로 변수가 들어가는 **데이터 세그먼트, 스택 세그먼트**.
- 이런 데 코드가 들어가면 실행되지 않게 만드는 게 NX 비트.

#### Code Reuse Attack과 Return-to-libc

- 코드를 주입하지 않고 코드를 재사용 하는 게 **Code Reuse Attack**.
- 프리한 다음 사용하기 때문에 문제가 되는데, 있는 코드를 그냥 재사용 하겠다. 그중에 하나가 **Return-to-libc**.
- 여기서 c는? : common 공통 라이브러리
- libc 안에 printf나 scanf 들어있음.
- 라이브러리에 있는 코드는 주입한 게 아니고 실행하려면 필요함. 거기로 리턴하겠다. 이 부분을 **Code Reuse Attack**.

| 필요한 상황 | 링크 옵션 |
|---|---|
| cos, tan 이런 거 쓸 때 | `-l math` 라이브러리를 가져오겠다 |
| pthread create 할 때 | `-l pthread` library |

#### 공격 종류 정리

| 공격 | 설명 |
|---|---|
| **Code Injection Attack** | 이전에 배웠던 내용. 셸 코드를 주입하기 때문에 Code Injection Attack |
| **Code Reuse Attack** | 라이브러리 등에 있는 기존 코드를 재사용 (Return-to-libc 등) |
| **Control Hijacking Attack** | 두 개를 합쳐서 Control Hijacking Attack. 제어흐름을 가로채겠다. 변조하겠다. |

### 1. Control Flow와 Control Hijacking

#### 제어문 (control statement)

C언어 (데니스 리치와 켄 톰슨이 개발) 제어문 control statement :

| 종류 | 내용 |
|---|---|
| 순차문 | 제어문 이전에는 차례차례 순차적으로 실행됨(순차문 control statement). 하나의 문장이 있으면 다음 문장이 실행되고 또 그 다음 문장이 실행됨. 최소한 한 번씩 실행. |
| 조건문 (`if`, `switch`) | 조건이 나오면 조건에 만족되는 문장만 실행. |
| 반복문 (`for`, `while`, `do-while`) | 한 번이 아니라 여러 번 실행됨. |

- control statement 라고 함.

#### Control Hijacking Attack

- **Control Hijacking Attack** : 실행 흐름을 가로챈다
- 이전에 배운 것은 실행 흐름을 가로채서 셸 코드로 감 : 리턴 투 스택, 또는 리턴 투 셸코드 인 스택
- 여기는 return to libc : 라이브러리에 있는 function으로 가겠다

> **Control-flow hijacking = Code Injection Attack + Code Reuse Attack**

| 공격 | 방어 기법 / 특징 |
|---|---|
| Code Injection Attack | 리눅스는 **NX bit**, 윈도우는 **DEP**(Data Execution Prevention : 데이터 세그먼트에 코드가 들어가도 실행 못 하게 하겠다) |
| Code Reuse Attack | 공격자 입장에서 nx bit를 우회하자 해서 나온 공격 |

- 실습 환경 32bit
- ASLR과 관계 큼. 64bit로 가면 굉장히 강력
- **Control Flow Integrity** : 제어흐름을 무결성 유지하겠다
- PHP도 메모리 손상과 관련된 취약점

#### Control Flow 란?

| 구분 | 실행 단위 |
|---|---|
| 고급 언어 | 문장 |
| 기계어 | instruction |

- 프로그램이 실행될 때 문장들이 실행되는 순서(기계어에서는 instruction이 실행되는 순서).
- add, subtract, multiply, and, or 이런 인스트럭션도 있지만 함수도 들어옴.
- library 함수 같은 것. function call. 이것들이 어떻게 실행되는지 순서를 정하자.
- 실행되는 순서를 바꾸겠다. = **control flow hijacking**

#### control flow가 조작된다 = 어떤 레지스터가 조작된다?

| 용어 | 의미 |
|---|---|
| EIP | 프로그램 카운터. 다음에 실행할 명령어의 주소. 프로그램 카운터를 조작하겠다. (셸 코드로 뛰게 만들던지 리턴 주소를 조작하던지. function pointer로 함수에 대한 포인터 변수를 조작) 우리는 프로그램 카운터라고 말하지만 intel이나 AMD는 32비트에서 eip, 64비트에서 rip. |
| Function Pointer | 호출할 함수의 주소를 저장하는 변수 |

### 2. CFG (Control Flow Graphs)

#### 구성 요소

| 요소 | 설명 |
|---|---|
| 그래프 | 노드 + 엣지 |
| 노드 | 노드를 만드는 것이 **Basic Block** |
| 엣지 | flow니까 실행 흐름이 있어야 함. 어떤 노드가 먼저 실행이 되고 어떤 노드가 나중에 실행된다라는 방향이 있는 **directed edge**가 필요함. 일종의 순서도가 됨. |

> **Basic Block의 특징** : 무조건 그 순서대로, 한 번씩 실행됨. if가 나오면 무조건 실행된다는 보장이 없기 때문에 다른 베이직 블록이 됨.

```text
       [if 조건 판단]
        /       \
     참/         \거짓
 [처리 A]       [처리 B]
        \       /
        [다음 처리]
```

#### p.4 예제 코드

```c
x = z-2;
y = 2*z;
if (c) {
  x = x+1;
  y = y+1;
}
else {
  x = x-1;
  y = y-1;
}
z = x+y;
```

| 베이직 블록 | 내용 |
|---|---|
| B1 | `x = z-2; y = 2*z; if (c)` |
| B2 (T) | `x = x+1; y = y+1;` |
| B3 (F) | `x = x-1; y = y-1;` |
| B4 | `z = x+y;` |

- 4pg에서 베이직 블록은 4개
- 모든 프로그램은 컨트롤 플로우 그래프를 그릴 수 있음
- 노드의 개수가 많을 수도 있고 적을 수도 있음 : 복잡도
- 왔다갔다 표시있는 게 반복문

#### CFG를 이용한 방어

- CFG를 통해 방어할 수 있음.
- 공격자가 원하는 경로에 새로운 노드가 추가가 되면 어떤 공격? : **Code Injection Attack** 발생 → 코드가 주입되면 새로운 노드가 추가가 됨
- 간단하게 방어하는 것은 처음 CFG를 만들고 실행 중간에 노드 개수가 추가되면 누군가가 추가했다는 뜻. 그래프가 깨졌다 or 그래프가 무결성이 존재한다 보장된다. 이런 걸 가지고 공격을 방어함.
- 셸 코드를 주입하면 베이직 블록이 추가됨

#### 셸 코드와 기계어

- 셸 코드를 만드는 것은 어셈블리에 대한 지식을 필요로 함.
- 기계어 자체는 CPU나 OS에 종속적. A라는 CPU를 위해서 만든 기계어는 다른 CPU에서 사용 안 됨.
- 자바는 바이트 코드를 가지고 실행하지만 반드시 JVM이 필요함. 기계어로 되기 전 코드: 바이트 코드. 자바에서는 바이너리 코드라는 말을 안 씀.

```text
바이트 코드 → 자바 버츄얼 머신(JVM) → 바이너리 코드
```

- JVM이 없으면 바이트 코드가 의미 없음. 돌아가지 않음.

### 3. C 함수 포인터 복습 (p.7)

#### p.7 코드

```c
#include <stdio.h>
// A normal function with an int parameter and void return type
void fun(int a) {
    printf("Value of a is %d\n", a);
}

int main(void) {
    // fun_ptr is a pointer to function fun()
    void (*fun_ptr)(int) = fun;  // fun == &fun
    /* The above line is equivalent of following two
       void (*fun_ptr)(int);
       fun_ptr = &fun; */

    // Invoking fun() using fun_ptr
    (*fun_ptr)(10);  // == fun (10);
    return 0;
}
```

```c
#include <stdio.h>
int (*v)(int);
/* v is not itself a function but rather is a variable
   that can point to a function. */

int f(int x) {
    return x+1;
}

void main(void) {
    v = f;
    printf("%d\n", (*v)(3) );
}
```

#### 함수 포인터 설명

| 코드 | 설명 |
|---|---|
| `void (*fun_ptr)(int) = fun;` | 함수에 대한 포인트 변수를 줌. 함수에 대한 포인터 변수에 이름을 값으로 줌. = 함수 이름 자체가 주소가 됨. 함수에 대한 포인터를 선언하고 값을 주는 것과 2문장으로 하든 1문장으로 하든 똑같음. |
| `(*fun_ptr)(10);` | 호출할 때는 10이라는 인자를 줌. 부르면 호출이 됨. |
| `int (*v)(int);` | 함수에 대한 포인터 변수 선언. **v가 변수임.** |
| `v = f;` → `(*v)(3)` | 함수에 대한 정의가 있고 함수에 대한 포인터 변수에 값을 주고 v에다 f를 줌. 그 다음 함수를 호출함. (`v(3)`의 결과는 4) |

- 포인터는 무조건 주소. 함수 이름, 배열 이름도 주소.
- 배열은 변수니까 데이터 세그먼트, 스택 세그먼트에 있음. 함수는 코드 세그먼트에 있음(주소가 낮음).
- 포인터 변수 앞에 `*`를 쓰면 **역참조**

#### 함수와 관련된 용어 (p.7 코드 기준)

| 용어 | 설명 |
|---|---|
| 함수 호출 | `(*fun_ptr)(10);` 처럼 함수를 부르는 것 |
| 함수 정의 | main 위에 먼저 정의되어 있으면 컴파일러가 먼저 존재를 앎. |
| 함수 선언 | main 아래에 함수 정의가 있으면 main 부터 번역. fun 이 나오면 모르는 심볼임. 함수 선언이 필요. |

- printf의 정의는 어디에? header파일에는 **선언**이 있음. **정의**는 라이브러리에 있음. 라이브러리를 링킹함.
- user defined 함수와 library defined 함수가 있음
- stdio 는 standard input output의 준말 : 표준입력: scanf / 표준 출력: printf

#### 스택 vs 힙 버퍼 오버플로우 조건

| | 스택 | 힙 |
|---|---|---|
| 공격 대상 | 스택의 return address | function pointer |
| 필요한 조건 | 버퍼가 지역변수에 있어야 함. 안전하지 않은 취약함수(scanf, strcpy, gets, memcpy) | 버퍼가 있고, 함수에 대한 포인터 변수, 취약 함수(gets) |
| 원리 | 버퍼를 넘치게 만들어서 스택의 return address를 조작함. return address가 program counter로 감. 그래서 return address를 조작함. | 힙에는 return address가 없음. r.a.와 비슷한 뭔가가 필요함. 힙에 버퍼 오버플로 공격을 하려면 function pointer가 있어야 함. |

- **힙 버퍼 오버플로우** : 힙에서 버퍼를 넘치게 만들어서 컨트롤 플로우를 하이재킹함.
- function pointer가 없으면 힙에서는 버퍼 오버플로 공격을 하기 어려움. 더블 프리 어택(같은 할당을 두 번 free함) 같은 다른 공격해야 함.

### 4. 힙 오버플로우를 이용한 코드 주입 (p.8)

힙에서 Code Injection Attack을 하는 것 (8pg)

#### p.8 코드

```c
/* record to allocate on heap */
typedef struct chunk {
    char inp[64];            /* vulnerable input buffer */
    void (*process)(char *); /* pointer to function to process inp */
} chunk_t;

void showlen(char *buf)
{
    int len;
    len = strlen(buf);
    printf("buffer5 read %d chars\n", len);
}

int main(int argc, char *argv[])
{
    chunk_t *next;

    setbuf(stdin, NULL);
    next = malloc(sizeof(chunk_t));
    next->process = showlen;
    printf("Enter value: ");
    gets(next->inp);
    next->process(next->inp);
    printf("buffer5 done\n");
}
```

#### 코드 설명

| 코드 | 설명 |
|---|---|
| `typedef struct chunk { char inp[64]; void (*process)(char *); } chunk_t;` | 구조체 멤버 2개 inp, process. 어떤 게 낮은 주소? **inp가 낮은 주소.** |
| `main` | 사용자가 정의한 함수, main 있음 |
| `setbuf(stdin, NULL);` | stdin 이게 표준 입력. |
| `next = malloc(sizeof(chunk_t));` | malloc을 통해 구조체 할당. 힙 영역에 잡힘. 이 구조체는 힙에 할당. 그래서 힙 오버플로. |
| `next->process = showlen;` | 함수에 대한 포인터이기 때문에 함수 이름(주소)을 값으로 줌. |
| `gets(next->inp);` | 버퍼를 읽어들임. 버퍼가 64바이트 이내면 문제 없음. (취약 함수) |
| `next->process(next->inp);` | 함수 호출. 이게 argument로 가서 출력이 됨. 64바이트보다 적게 주면 정상 실행. |

#### 메모리 위치

- 배열에서 inp[0]과 inp[1] 중 낮은 주소는? inp[0]. 앞쪽에 있는 게 무조건 낮은 주소. 뒤에 있는 게 높은 주소.
- 구조체도 마찬가지로 배열과 비슷함.
- 배열은 같은 멤버들이 같은 타입으로 갖고, 구조체는 같은 멤버들이 다른 타입을 갖는 것이 차이점.
- 메모리 위치가 중요함. **inp가 넘치면 process 값이 조작됨.**

#### function pointer는 언제 사용?

| 사용처 | 설명 |
|---|---|
| pthread 사용할 때 | |
| GOT | 함수에 대한 포인터가 가지고 있는 테이블. 라이브러리 함수에 대한 주소를 가지고 있음. 그게 함수에 대한 포인터. |
| system call table | 함수에 대한 주소가 들어가 있음 |

#### 공격자들은 이런 걸 찾음

- 버퍼가 있고, 버퍼보다 높은 주소에 함수에 대한 포인터가 있고, gets라는 취약함수도 있음.
- → 잘하면 공격할 수 있다. 역공학 하면 보임.

#### 공격자가 줘야 하는 입력 길이

| 입력 길이 | 결과 |
|---|---|
| 64바이트 이내 (64바이트보다 적게) | 정상 실행 |
| 최소 65바이트 | 버퍼를 넘치게 함 |
| **68바이트** | 함수에 대한 포인터 변수(process)까지 조작. 처음에는 showlen이었는데 다른 주소로 바꿀 수 있음. |

- 공격자는 몇 바이트를 주나? 버퍼를 넘치게 해야하니까 최소한 65바이트. 제대로 공격하려면 아까 함수에 대한 포인터 변수를 조작해야함. 몇 바이트 줘야함? 68바이트.
- 카운트 해보지 않아도 68바이트.

| 입력 구성 | 설명 |
|---|---|
| 앞 64바이트 | 90은 nop. 90이 아닌 건 셸 코드. 셸 코드 길이가 대강 30바이트보다 적음. 64바이트니까 이 안에 들어갈 수 있음. |
| 마지막 4바이트 | process에 들어감. 이게 넘치면서 나머지 4바이트가 덮어씀. showlen이 덮어쓴 이 값으로 바뀜. 이 값은 아마도 nop 중에 하나를 가리킴. |

- 이런 조건이 될 때 힙에서 발생할 수 있는 **Code Injection Attack**.

#### 스택에서 힙으로

- 처음에는 스택에서 공격을 많이 함. 리턴 주소가 기본적으로 들어가니까. 스택에서 공격하기 쉬움.
- 지역 변수에 버퍼를 아는 경우가 많고 취약 함수가 많았음. gets, scanf, strcpy, strcat, sprintf.
- ASLR을 쓰면서 스택 주소를 랜덤화 시킴. 공격이 어려워져서 스택이 아닌 힙으로 감. 힙으로 가서 Code Injection을 개발함.

### 5. Code Injection vs Code Reuse — CFG 관점

#### Code Injection (p.9)

- CFG로 보면 원래 개발자가 만든 프로그램에는 노드가 6개밖에 없었음.
- Code Injection이 되면 새로운 노드가 추가됨. 하나가 추가되든 두개가 추가되든 새로운 노드가 추가됨.
- 공격자가 뭔가를 조작해서 자기가 추가한 노드로 점프하게 만들면 Code Injection Attack.
- 그래프를 관찰하면 Code Injection Attack을 간단하게 유추할 수 있다. 새로운 노드가 추가되었는지 아닌지만 확인하면 됨. 노드의 개수만 가지고 있어도 됨.

#### NX 비트와 Code Reuse의 등장

- Code Injection이 스택에도 될 수 있고 힙에도 될 수 있음.
- 이런 코드 실행을 막자, 셸 코드가 주입됐다면 막자 해서 나온 게 **nx 비트**.
- 그러면 이제 코드를 주입하지 않고 공격을 해보자 그래서 나온 게 **Code Reuse Attack**.
- 오리지널 프로그램 코드 내에 있는 기존의 코드를 그대로 씀. 쓰긴 쓰는데 실행 흐름을 조작. 다르게 말하면 노드 수는 그대로 두고 엣지만 바꿈.
- 나중에 방어 기법 **컨트롤 플로우 인테그리티**. 컨트롤 플로우의 무결성만 확인하자.

| | Code Injection Attack | Code Reuse Attack |
|---|---|---|
| CFG 변화 | 노드, 엣지 추가됨 | 노드는 그대로 두고 엣지만 바꾸겠다. |
| 사용하는 코드 | 주입한 셸 코드 | 오리지널 프로그램 코드 내에 있는 기존의 코드 |
| 방어 | nx 비트 | 컨트롤 플로우 인테그리티 |

#### Code Reuse Attack의 발전

| 단계 | 내용 |
|---|---|
| ① return to libc | Code Reuse Attack도 처음에는 return to libc로 감. |
| (방어) | libc에서 불필요한 함수 빼버림. 공격에 사용되니까 빼버리자. 시스템을 이용하지 못하게 만들자. 주소를 영역에 배정시키면 됨. 그러면 카피할 때 문제가 생김. |
| ② **ROP** | 그러면 함수를 통째로 없애도 되겠다. 함수가 없어도 공격하겠다. 조금 더 일반화 된 공격. return으로 끝나는 조각들을 활용. 함수가 들어가면 리턴으로 끝나기 때문에 많을 수밖에 없음. |
| ③ **JOP** | 그러면 return을 없애버리겠다. 리턴 문장을 점프로 바꿔버림. 점프를 이용해서 공격. |

### 6. 힙 버퍼 오버플로 vs 스택 버퍼 오버플로 (p.12)

이번 챕터에서 하는 실험은 힙 버퍼 오버플로 스택 버퍼 오버플로 차이점 비교

| | Heap Overflow | Stack Overflow |
|---|---|---|
| Target of modification | Function Pointer | Return Address |
| Executable target | `runsh()` inside program | `system()` in libc |
| Core mechanism | Indirect Call Hijacking | Return Address Hijacking |
| Necessity of Code Injection | No | No |

- 코드를 주입하지는 않음
- 힙에서는 function pointer 가 있음. 스택은 return address가 있음
- Code Reuse Attack을 해야하기 때문에 run shell이라는 함수를 일부러 집어넣음. 라이브러리에 있는 system 함수를 활용.
- 힙 오버플로의 핵심적인 공격 매커니즘 : **indirect call을 hijack** 하는 것. 함수에 대한 포인터를 공격해 조작하는 거니까 indirect hijacking.
- 스택에서 Code Reuse Attack은 **return address를 hijack** 하는 것.
- r.a.를 조작하는 것은 똑같으나 코드를 주입하느냐(Code Injection) 재사용하느냐(Code Reuse)의 차이.
- 코드를 재사용하기 때문에 라이브러리에 있는 시스템을 재사용하겠다는 의미가 됨.


### 7. 힙 함수 포인터 변조 — 코드 주입 없이 (p.13~17)

#### 7-1. 실습에서 확인할 내용 (p.13)

힙에서 **function pointer를 하이재킹해서 어떻게 실습할 수 있는가.**

- 셸 코드를 주입할 필요 없음. 그래서 **inp 버퍼의 크기를 작게 만듦.**
- 버퍼를 입력으로 받는데, **넘치지 않게 하는 것 1번, 넘치는 것 1번**을 확인함.
- 버퍼가 넘치면 망가짐 → 원하는 것으로 바꿀 수 있음.

| 확인할 내용 | 설명 |
|---|---|
| function pointer를 하이재킹하려면 버퍼에 주입해야 하는 데이터의 길이? | **12바이트** |
| main에서 정상적이라면 부르는 함수 | `showbuf` |
| 정상적인 함수 호출 횟수 | `showbuf`에 대한 콜이 **2번** |
| 두 호출 사이에 있는 함수 | `strcpy`라는 취약 함수 |
| 공격이 발생하지 않으면? | `showbuf`가 두 번 불림 |

#### 7-2. PDF의 기존 코드 (p.13~15)

아래는 PDF에 있는 `heap_bof.c` 코드임. PDF의 여러 칸에 나뉜 코드를 구조체 → 함수 → `main` 순서로 모아 적음.

```c
/* heap_bof.c */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct chunk {
    char inp[8];
    void (*proc)(char *);
} chunk_t;

void showbuf(char *buf) {
    printf("buf = %s\n", buf);
}

void runsh(char *buf) {
    system("/bin/sh");
    printf("buf = %s\n", buf);
}

int main(int argc, char *argv[])
{
    chunk_t *next;
    next = malloc(sizeof(chunk_t));
    printf("inp=%p, proc=%p\n", next->inp, &(next->proc));
    printf("runsh =%p\n", runsh);
    next->proc = showbuf;
    next->proc(next->inp);
    strcpy(next->inp, argv[1]);
    next->proc(next->inp);
    printf("Heap buffer done\n");
}
```

※ 아래 설명에서 적은 **런셸 / runshell은 PDF 코드의 `runsh()`**를 가리킴.

#### 7-3. 32비트 컴파일과 주소 확인 (p.13)

```bash
gcc -m32 -o heap_bof heap_bof.c
```

- **32bit용으로 하기 위해 컴파일함.** 스택에 대한 보호 기법은 의미 없음.
- `heap_bof` 실행. `argv[1]`이 있으니까 입력으로 주려고 **7바이트**를 줌.
- 버퍼는 넘치지 않고 정상적인 실행이 됨.

| 코드 / 출력 대상 | 확인하는 내용 |
|---|---|
| `printf("inp=%p, proc=%p\n", next->inp, &(next->proc));` | `inp`의 주소와 `proc`의 주소를 출력. 어느 것이 낮은 주소고 높은 주소인지 확인 |
| `inp`와 `proc` 비교 | **inp가 낮은 주소, proc이 높은 주소** |
| `inp`가 넘치면? | **proc이 망가질 수 있음** |
| `printf("runsh =%p\n", runsh);` | 기존 코드를 재사용해야 하니까 런셸의 주소 출력 |
| `next->proc = showbuf;` | 함수를 할당. 함수 포인터에 대해 설정함 |
| `next->proc(next->inp);` | 설정한 함수를 콜함 |

#### 7-4. 정상적인 실행 — 7바이트 입력 (p.13)

PDF의 정상 입력 실행 명령:

```bash
./heap_bof `perl -e 'print "A"x7'`
```

| 순서 | 해당 코드 | 설명 / 결과 |
|---|---|---|
| ① 첫 번째 호출 | `next->proc(next->inp);` | `inp`에 아무것도 안 줌. `inp`가 비어 있어서 비어 있는 출력이 나옴. 첫 번째 버퍼는 `inp`가 비어 있어서 출력 |
| ② 입력 복사 | `strcpy(next->inp, argv[1]);` | 여기서 `strcpy`를 함. `argv[1]`은 7바이트. `inp`로 줌 |
| ③ 두 번째 호출 | `next->proc(next->inp);` | 다시 `showbuf` 호출. 두 번째 호출하면 입력으로 준 **A가 출력** |

⇒ 이건 **정상적인 실행**. 공격이 발생하지 않아서 `showbuf`가 두 번 불림.

#### 7-5. 공격하는 경우 — 12바이트 입력 (p.13~14)

공격하면 **12바이트**를 줌. 8바이트는 아무거나 줘도 됨. **뒤에 있는 4바이트가 중요함.**

| 입력 구성 | 의미 |
|---|---|
| 앞의 8바이트 | 아무거나 줘도 됨 |
| 뒤의 4바이트 | **런셸의 주소를 리틀 엔디안으로 줌** |

```text
[ 앞의 8바이트 ][ 뒤의 4바이트             ]
[ inp를 채움   ][ 런셸의 주소: 리틀 엔디안 ]
```

- 본래는 `showbuf`가 들어가 있음.
- 여기서 버퍼를 넘치게 만들면서 **런셸의 주소로 바꿔치기**함.
- 실제로 바꿔서 호출함. 첫 번째는 `showbuf`, 두 번째는 `runshell`이 불림. 이 주소가 런셸을 불리게 만들었기 때문임.

| 순서 | 코드 / 명령 | 설명 / 결과 |
|---|---|---|
| ① 첫 번째 함수 호출 | 첫 번째 `next->proc(next->inp);` | `showbuf`가 불림 |
| ② 버퍼를 넘침 | `strcpy(next->inp, argv[1]);` | 런셸의 주소로 바꿔치기 |
| ③ 두 번째 함수 호출 | 두 번째 `next->proc(next->inp);` | `runshell`이 불림 |
| ④ 새로운 셸 실행 | `system("/bin/sh");` | 런셸이 불리면 새로운 셸을 띄우게 됨 |
| ⑤ 셸 확인 | `ps` | 셸이 두 개가 됨 |
| ⑥ 새 셸 종료 | `exit` | 최근에 생성된 셸을 종료. 이전의 셸로 되돌아감 |
| ⑦ 버퍼 출력 | `printf("buf = %s\n", buf);` | 이전의 셸로 되돌아가서 `printf`가 실행. **8문자가 출력되고 아스키코드로 뭔가 출력됨** |
| ⑧ 함수 반환 후 | `printf("Heap buffer done\n");` | return되면 다시 이쪽으로 와서 `Heap buffer done` 출력 |

이게 공격하는 간단한 예. **코드를 주입하지 않음. 있는 코드를 재사용함 → Code Reuse Attack.**

이런 자료 구조에 `strcpy`가 있기 때문에 가능함.

#### 7-6. 리눅스의 다른 배포판 예시 — 주소와 세그먼트 (p.14)

| 확인할 주소 | 어느 세그먼트인가? / 설명 |
|---|---|
| inp가 가리키는 주소는 어느 세그먼트인가? (proc에 할당된 주소) | **힙**. `malloc`을 했기 때문 |
| runshell의 주소는? | **code segment** |
| 스택에 있는 주소 | 지역 변수. `bf`로 시작하고 8자리. 위 주소들과 큰 차이가 있음 |
| runsh의 주소 | 이것도 8자리이지만 `bf`보다는 훨씬 작음 |

#### 7-7. 64비트의 예시 (p.15)

PDF에서는 앞의 `heap_bof.c`와 같은 구조체·함수 코드를 사용함.

| 구분 | 설명 |
|---|---|
| 사용하는 주소 비트 수 | **48bit만 씀** |
| 64비트를 다 쓰지 않는 이유 | 64비트를 쓸 수는 있지만 너무나 큰 주소이기 때문에 다 쓰지는 않음 |
| 32비트와 64비트의 차이 | 주소를 나타내는 비트 수가 완전히 다름 |
| 64비트에서 실습을 제대로 하려면? | **앞의 8바이트 뒤에 런셸 주소의 하위 6바이트를 붙여서 원하는 주소로 바꿔치기함** |

- 주소 체계에 따라서 다름.
- **핵심은 코드를 주입한 게 아니라 있는 코드를 재사용한 것임.**

#### 7-8. Code Reuse Attack을 CFG로 보면 (p.16~17)

| 구분 | 설명 |
|---|---|
| Code Reuse Attack | CFG에서 **노드 수는 달라지지 않지만 엣지만 달라짐**. 기존에 있는 코드를 재사용함 |
| Return-to-libc | 함수를 쓰기 때문에 이런 그래프와 조금 다름. **하나의 함수 안에 여러 Basic Block이 있음** |
| ROP 공격 | 이 그래프와 정확한 것은 ROP 공격. 원하는 **코드 조각을 이어서 공격**하기 때문 |

| 그래프의 색상 | 의미 |
|---|---|
| 파란색 노드 | 본래 개발자가 만든 오리지널 노드 |
| 하늘색 엣지 | 기존 엣지들 |
| 빨간색 엣지 | Code Reuse Attack을 하면 **새로운 엣지가 추가됨** |

### 8. W^X, NX bit, DEP (p.19~20)

#### 8-1. W^X 정책

| 기호 | 의미 |
|---|---|
| `W` | Writable, 쓰기 가능 |
| `X` | Executable, 실행 가능 |

- **W^X = 한 페이지에 W와 X를 동시에 허용하지 않는 것.**
- 보통 **페이지 단위**로 권한을 관리하며, 흔한 기본 페이지 크기는 **4 KiB**임. 모든 시스템의 페이지가 반드시 이 크기는 아님.
- 가능한 한 어떤 페이지는 writable만 하고 실행은 안 되게, 반대로 실행 가능한 페이지는 write가 안 되게 하는 게 좋음.

| 페이지 성격 | 바람직한 권한 |
|---|---|
| 데이터 (스택, 힙, 변수) | W만 허용, X 불가 |
| 코드 | X만 허용, W 불가 |

※ 예외로 강의에서는 **힙에서 돌아가는 코드(자바, GC를 함)**와 **스택에서 돌아가는 코드(`longjmp`, `setjmp`)**를 언급함.

#### 8-2. NX(No-eXecute) bit

- W^X를 **구체적으로 구현한 것**이 NX bit.
- 페이지 테이블에는 **페이지 테이블 엔트리(PTE)**가 있고, 엔트리에는 여러 제어 비트가 들어감.
  - 예: Dirty bit, Use(참조) bit 등. 페이지 교체 정책으로는 LRU를 많이 씀.
- 여기에 **비트를 하나 더 추가한 것이 NX bit**.

| NX bit | 의미 |
|---|---|
| **ON** | 이 페이지는 **실행 불가** |
| **OFF** | 이 페이지는 **실행 가능** |

| 영역 | NX bit | 이유 |
|---|---|---|
| 코드 세그먼트 | OFF | 당연히 실행 가능해야 함 |
| 스택, 힙, 데이터 | ON | 변수가 들어가는 영역이기 때문 |

#### 8-3. Windows의 DEP

- Windows에서는 **DEP(Data Execution Prevention)**라는 용어를 사용함.
- **NX는 하드웨어 기능**, **DEP는 이를 활용하는 보호 기능**이라는 층위 차이가 있음.

```text
스택에 셸코드 복사      → 쓰기 권한이 있으면 복사 자체는 가능
명령어 포인터가 스택 이동 → NX가 설정되어 있으면 실행 차단
                       → 강의 환경에서는 Segmentation fault
```

**NX가 막는 것과 못 막는 것**

- 주입한 셸코드의 실행은 차단할 수 있음.
- **버퍼 오버플로우나 반환 주소 변경 자체를 막는 것은 아님.**
- 변조한 주소가 실행 가능한 라이브러리 코드라면 NX 위반이 아님 → 코드 재사용이 가능해짐.

> 보충 : 강의에서 힙·스택의 코드 실행 예외가 언급됨. 동적 코드 생성(JIT)에는 실행 가능한 메모리가 필요할 수 있지만 Java의 객체 힙·GC와 같은 개념은 아님. 또한 `setjmp`/`longjmp` 자체가 실행 가능한 스택을 요구하는 것은 아님.

### 9. Non-executable Stack 실험 (p.23~25)

강의의 `shellcode.c`는 저장된 코드 바이트를 지역 배열로 복사한 뒤 함수 포인터로 해석해 호출함.

```c
// code: 강의에 제시된 기계어 바이트 배열
char buffer[sizeof(code)];
strcpy(buffer, code);
((void (*)(void))buffer)();
```

- 전역의 `const char code[]` : 정적 저장 기간을 가진 배열이며 보통 읽기 전용 데이터 영역에 배치됨.
- 지역 변수 `buffer` : 강의의 구현에서는 스택에 배치됨.
- `(void (*)(void))buffer` : 주소를 함수 포인터로 해석
- 마지막 `()` : 그 주소를 호출
- **타입 캐스팅만 한다고 페이지에 실행 권한이 생기는 것은 아님.** 이 코드는 환경 의존적인 실행 실험임.

강의의 32비트 Linux 셸코드에서는 `0x68`이 `push` 명령을 나타내고, `int 0x80`으로 시스템 호출을 요청함. `execve`의 시스템 호출 번호 `11(0x0b)`도 **그 ABI 기준**임.

| 컴파일 옵션 | 강의에서 관찰한 결과 |
|---|---|
| `-z execstack` | 스택 코드 실행 → 새로운 셸 |
| `-z noexecstack` | 스택 코드 실행 차단 → Segmentation fault |

⇒ 같은 바이트를 넣어도 **해당 메모리 영역의 실행 권한**에 따라 결과가 달라짐.

### 10. Return-to-libc의 기본 원리 (p.21~23, 26~27, 33)

> **Return-to-libc(Ret2Libc)** : 반환 주소를 libc 안의 함수 주소 등으로 바꾸어, 이미 존재하는 실행 가능한 코드를 재사용하는 기법

- `libc`는 **C 라이브러리**를 뜻하며, 일반적인 C 프로그램에서 널리 사용됨. 강의의 “공통적으로 쓰는 라이브러리”는 그 성격을 설명한 것임.
- 표준 C 함수가 일반적인 빌드에서 연결되는 것과 달리, math 라이브러리 등은 환경에 따라 별도 링킹 옵션이 필요함.
- 수학 라이브러리 옵션은 보통 `-lm`임. 스레드 관련 옵션은 일반적으로 `-pthread`를 사용하며 라이브러리 분리 여부는 환경마다 다를 수 있음.
- 이번에 재사용하는 함수는 `system()`임.

```c
system("/bin/sh");
```

- `system()`은 명령 문자열을 받아 셸을 통해 실행함.
- `/bin/sh`는 실행할 셸을 지정하는 **문자열 데이터**임.
- **`"/bin/sh"` 문자열과 셸코드는 다름.** 문자열은 인자로 읽히며 CPU 명령어로 실행되는 것이 아님.
- 스택에는 주소·문자열 등 데이터만 놓고, 실제 명령어는 실행 가능한 라이브러리 영역에서 가져옴.

**왜 NX를 켠 채로 성공할 수 있을까?**

```text
코드 주입 : ret → 스택에 주입한 기계어 실행 → NX가 차단
Ret2Libc  : ret → libc의 system 코드 실행  → 실행 가능한 영역
                         ↑
              스택의 인자 포인터를 데이터로 읽음
```

⇒ **NX를 끄거나 스택을 실행 가능하게 만드는 것이 아니라, NX가 금지하지 않는 기존 코드 실행을 이용함.**

### 11. 필요한 정보와 32비트 호출 규약 (p.23, 27~33, 36)

| 알아야 할 정보 | 필요한 이유 |
|---|---|
| 버퍼에서 저장된 반환 주소까지의 거리 | 정확한 위치를 덮어쓰기 위해 |
| `system()`의 주소 | 반환 시 이동할 대상 |
| `"/bin/sh"` 문자열의 주소 | `system()`에 전달할 인자 값 |
| 인자를 놓을 스택 위치 | 함수가 예상하는 위치에서 인자를 읽도록 하기 위해 |
| `exit()` 등의 후속 주소 | `system()` 반환 이후의 흐름을 정하기 위해 |

**이번 스택 배치는 x86 32비트 cdecl 기준**

- 인자는 스택으로 전달하며, 여러 인자를 준비할 때는 일반적으로 오른쪽 인자부터 놓음.
- 일반적인 `call`은 복귀 주소를 스택에 저장한 후 함수로 이동함.
- 전형적인 함수 프롤로그가 프레임을 만들면 `EBP`가 기준점이 됨.
- `ret`은 스택에서 주소를 꺼내 명령어 포인터로 사용함.
- **x86-64 Linux에서는 앞쪽 정수·포인터 인자를 RDI, RSI, RDX 등의 레지스터로 전달**하므로 이 배치를 그대로 옮기면 안 됨.

### 12. `echo()` 예제로 스택 배치 이해 (p.28~33)

```c
void echo(void) {
    char buffer[80];
    gets(buffer);
    puts(buffer);
}

int main(void) {
    echo();
    printf("Done");
    return 0;
}
```

- `gets()`가 길이를 제한하지 않아 지역 버퍼 뒤를 덮을 수 있음.
- **스택이 성장하는 방향과 문자열 복사가 진행되는 방향은 다름.** 스택 프레임은 낮은 주소 쪽으로 늘어나지만, `buffer[0]`, `buffer[1]`, …로 복사하는 쓰기는 높은 주소 쪽으로 진행하므로 뒤의 saved EBP와 반환 주소에 도달할 수 있음.
- 아래 계산은 **80바이트 버퍼와 saved EBP 사이에 추가 패딩이 없다고 가정**한 설명임.
- 실제 오프셋은 어셈블리·컴파일 옵션·정렬을 확인해야 함. `buffer[80]`만 보고 항상 84바이트라고 결정하면 안 됨.

```text
낮은 주소 → 높은 주소

[ buffer 80바이트 ][ saved EBP 4바이트 ][ 원래 반환 주소 ]

덮어쓴 뒤
[ A × 80 ][ B × 4 ][ system 주소 ][ exit 주소 ][ "/bin/sh" 주소 ]
                      ↑               ↑             ↑
                echo의 반환 대상  system의 반환 대상  system의 첫 인자
```

**중요 : `system` 바로 다음 칸은 인자 칸이 아니라 `system`의 반환 주소 칸임.**

자료 p.32의 바이트를 해석하면 다음과 같음.

| 내용 | 값 | 낮은 주소부터 저장되는 바이트 |
|---|---|---|
| 버퍼 채움 | `A` 80개 | 80바이트 |
| saved EBP 덮어씀 | `B` 4개 | 4바이트 |
| `system` 주소 | `0xb7e5f430` | `30 f4 e5 b7` |
| `exit` 주소 | `0xb7e52fb0` | `b0 2f e5 b7` |
| 문자열 주소 | `0xbffffe8c` | `8c fe ff bf` |

- 총 **96바이트**의 예시 배치이며 입력 함수가 덧붙이는 널 문자는 별도로 고려함.
- 이 값들은 **슬라이드의 예시 주소**임. 다른 프로세스나 환경에서 그대로 사용할 수 없음.

**실행 흐름**

1. `gets()`가 반환 주소와 그 뒤의 데이터를 덮음.
2. `echo()`의 에필로그가 실행되고 `ret`이 변조된 주소를 꺼냄.
3. EIP가 `system()`을 가리킴. 이때 ESP는 준비한 `exit` 주소 칸을 가리킴.
4. `system()`은 다음 칸에서 문자열 포인터를 인자로 읽고 명령을 실행함.
5. 명령 실행이 끝나 `system()`이 반환하면 준비한 `exit()` 쪽으로 이동함.

- 후속 반환 주소가 잘못되면 셸 실행 뒤에도 프로세스가 비정상 종료될 수 있음.
- `exit`를 배치한 목적은 후속 제어 흐름을 정의하는 것임. **이 간단한 배치가 `exit(0)`의 인자까지 정확하게 준비한 것은 아님.**
- `exit()`로 종료하면 원래 `main()`의 `printf("Done")`으로 돌아가는 흐름과도 다름.

### 13. 실습 환경과 취약한 `stack.c` (p.34~35)

```text
main의 str[240]
    ← badfile에서 최대 200바이트 읽기
    → vul_func(str)
        → 지역 buffer[50]에 strcpy로 복사
```

- 읽어 둔 데이터를 더 작은 버퍼로 길이 검사 없이 복사하는 것이 취약점임.
- `strcpy()`는 원본에서 널 문자를 만날 때까지 복사하므로, 실제 복사량은 문자열 내용에 따라 달라짐.
- `fread()` 자체는 문자열 종료 널 문자를 자동으로 추가하지 않음. 자료의 코드에는 이 점에 대한 별도 처리도 필요함.
- 앞의 `echo()`는 80바이트, 여기의 `vul_func()`는 50바이트, p.27 개념 그림은 100바이트임. **서로 다른 예시의 크기를 섞으면 안 됨.**

| 설정 | 강의 실습 상태 | 의미 |
|---|---|---|
| NX / non-executable stack | **ON** | 스택에서 주입 코드를 실행하지 못하게 함 |
| StackGuard / 스택 카나리 | OFF | 반환 전 스택 손상 검사를 배제함 |
| ASLR | OFF | 주소 무작위화의 영향을 줄임 |
| 파일 소유자 | root | 권한 효과를 살펴보는 설정 |
| Set-UID | 설정 | 실행 파일 소유자의 유효 UID로 실행될 수 있게 함 |

- `-fno-stack-protector` : 해당 컴파일에서 스택 보호 코드 생성을 끔.
- `-z noexecstack` : 실행 불가 스택을 요청함.
- 슬라이드의 `kernel.randomize_va_space=0`은 ASLR 비활성화 설정이고, `chmod 4755`의 `4`는 Set-UID 비트를 의미함.
- Set-UID 실행과 실제 셸의 권한 유지 여부는 OS·셸 등의 동작에도 영향을 받음. **셸이 실행되었다는 사실만으로 root 셸을 얻었다고 단정할 수 없음.**
- 위 설정은 강의 실습 환경을 해석하기 위한 내용이며, 이 자료를 작성하면서 실행하거나 시스템 설정을 변경하지 않았음.

```bash
gdb stack
```

GDB 안에서 입력하는 명령:

```gdb
run

```

- GDB로 대상 실행 파일을 실행한 후 함수 주소를 확인하는 예제임.
- `p`는 `print`. `stack.c`의 실행에는 입력 파일 등 전제 조건도 갖춰져 있어야 함.
- p.37의 예시 결과는 `system = 0xb7e5f430`, `exit = 0xb7e52fb0`임.
- 이 값은 공유 라이브러리의 코드 주소이며, 스택의 문자열 주소와는 다른 영역에 있음.
- 강의에서는 코드의 낮은 주소, 라이브러리의 `b7...`, 스택의 `bf...` 등을 비교함. **주소 접두사·출력 자릿수는 해당 환경의 관찰값이며 영역을 판별하는 보편 규칙은 아님.**
- 주소에 `00` 바이트가 있으면 C 문자열 복사를 제약할 수 있음. 그렇다고 모든 널 포함 주소가 의도적으로 배치된 방어이거나 모든 오버플로우를 막는 것은 아님.

### 15. Task B — `"/bin/sh"` 문자열의 주소 (p.38~40)

> **문자열을 준비하는 것과 그 문자열이 대상 프로세스에서 어디에 있는지 아는 것은 별개의 문제임.**

```bash
export MYSHELL="/bin/sh"
echo "$MYSHELL"
printenv MYSHELL
```

- `export`한 환경 변수는 해당 셸에서 실행하는 자식 프로세스에 전달됨.
- `env`, 인자 없는 `printenv`로 환경 변수 목록을 확인할 수 있음.
- 강의 환경에서 초기 환경 문자열은 프로세스의 스택에 놓임.
- 환경 변수는 셸코드 보관용이 아니라 **`system()`이 사용할 문자열 데이터**를 준비하는 데 사용함.

주소 출력 예제를 표준 헤더와 포인터 출력 형식에 맞춰 정리하면 다음과 같음.

```c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    char *shell = getenv("MYSHELL");
    if (shell != NULL) {
        printf("Value: %s\n", shell);
        printf("Address: %p\n", (void *)shell);
    }
    return 0;
}
```

- `getenv()`는 변수의 **값 문자열을 가리키는 포인터**를 반환함. 없으면 `NULL`.
- `%s`는 문자열 내용, `%p`는 주소를 출력함.
- **이 보조 프로그램에서 출력한 주소가 취약한 프로그램의 주소와 같다고 보장되지 않음.**

**ASLR을 껐는데도 주소가 달라지는 이유**

- 실행 파일 이름, 인자, 환경 변수 등도 초기 메모리 배치에 영향을 줌.
- p.40에서 `env55`를 `env7777`로 바꾸자 예시 주소가 `bffffe8c`에서 `bffffe88`로 달라짐.
- 프로그램 이름 길이가 달라져 스택 배치가 바뀐 사례임.
- 강의에서는 추정 주소 근처를 조정하며 확인하는 접근도 설명함. 핵심은 **한 번 얻은 주소를 무조건 고정값으로 믿지 않는 것**임.

**GDB로 메모리를 확인하는 예**

```gdb
b main
run
x/100s *((char **) environ)
```

- `b main` : `main`에 중단점 설정
- `x` : 지정한 주소의 메모리 조사
- `100` : 반복 개수, `s` : 문자열 형식
- 위 표현식은 첫 환경 문자열을 가리키는 주소부터 연속된 문자열을 살펴보는 예제임. 환경 변수 배열을 정확히 100개 순회한다는 뜻은 아님.
- `MYSHELL=/bin/sh` 전체 문자열의 시작 주소와 **값 `/bin/sh`의 시작 주소를 구분**해야 함.
- 컴파일 옵션 `-g`는 디버깅 정보를 제공해 소스·심볼을 이용한 분석을 돕음. 강의에서는 배포 시 심볼 노출, 역공학, 난독화·안티 디버깅도 언급함. 디버깅 정보 제거가 메모리 취약점 자체를 해결하는 것은 아님.

### 16. Task C — 인자를 어디에 놓을까? (p.41)

> **`system()` 진입 직후에는 `ESP+4`, 전형적인 프롤로그가 끝난 뒤에는 `EBP+8`에 첫 인자가 있음.**

두 표현은 서로 다른 시점을 설명함.

**① `echo()`의 `ret`으로 `system()`에 막 진입했을 때**

```text
높은 주소
[ "/bin/sh" 문자열의 주소 ] ← ESP + 4 : 첫 인자
[ exit 주소                ] ← ESP     : system의 반환 주소
낮은 주소
```

**② `system()`의 전형적인 프롤로그가 프레임을 만든 뒤**

```text
높은 주소
[ "/bin/sh" 문자열의 주소 ] ← EBP + 8 : 첫 인자
[ exit 주소                ] ← EBP + 4 : 반환 주소
[ 이전 EBP 저장값          ] ← EBP
[ 지역 변수 등             ] ← ESP 쪽
낮은 주소
```

- `push ebp`가 ESP를 4바이트 낮추고 이전 EBP를 저장한 뒤, `mov esp, ebp`(AT&T의 원본·목적지 순서)가 그 위치를 새 EBP로 정함. 따라서 같은 인자 칸이 진입 시 ESP 기준으로는 `+4`, 새 EBP 기준으로는 `+8`이 됨.
- **`EBP+8` 칸에는 문자열 자체가 아니라 문자열을 가리키는 주소가 들어감.**
- 여기서 EBP는 **`system()`의 프레임 기준점**임. 취약 함수의 원래 EBP와 혼동하면 안 됨.
- 정상적인 `call system`을 실행하지 않아도, 함수 진입 시 스택이 기대하는 모양이면 기존 함수가 인자를 해석할 수 있음.
- “프롤로그 이후 모양을 만들어 준다”는 설명은 **정상 프롤로그 실행 후 올바른 배치가 되도록 진입 전 스택을 준비한다**는 뜻으로 이해해야 함. 프롤로그를 건너뛴다는 뜻은 아님.

### 17. Function Prologue — 스택 프레임 생성 (p.42)

> **프롤로그** : 함수 실행 초기에 이전 프레임 정보를 보관하고 현재 함수의 작업 공간을 마련하는 명령어 구간

- `ESP` : 현재 스택 꼭대기를 가리키는 **Stack Pointer**
- `EBP` : 현재 함수의 인자·지역 변수 참조 기준인 **Frame Pointer**
- 강의의 스택은 **낮은 주소 방향으로 성장**함.
- 아래 코드는 AT&T 문법이며 `명령 원본, 목적지` 순서임.

```asm
pushl %ebp
movl  %esp, %ebp
subl  $N, %esp
```

| 단계 | 동작 | 레지스터·메모리 변화 |
|---|---|---|
| 함수 진입 직후·프롤로그 실행 전 | 호출자가 인자를 준비하고 `call`이 반환 주소 저장 | ESP가 반환 주소를 가리킴 |
| `pushl %ebp` | 호출자의 EBP 보관 | ESP가 4 감소하고 그 위치에 이전 EBP 저장 |
| `movl %esp, %ebp` | 현재 프레임 기준점 지정 | EBP = ESP |
| `subl $N, %esp` | 지역 변수 등을 위한 공간 확보 | ESP가 N만큼 감소, EBP는 유지 |

```text
높은 주소
[ 두 번째 인자 ] ← EBP + 12
[ 첫 번째 인자 ] ← EBP + 8
[ 반환 주소    ] ← EBP + 4
[ saved EBP    ] ← EBP
[ 지역 변수    ] ← EBP보다 낮은 주소
[ 패딩 등      ] ← ESP
낮은 주소
```

- **EBP는 기준점으로 유지되고 ESP는 push/pop·공간 할당에 따라 변함.**
- `N`에는 지역 변수 외에 정렬용 패딩 등의 공간도 포함될 수 있음.
- 따라서 소스 코드의 배열 크기와 실제 스택에서 확보한 공간이 같다고 단정할 수 없음.
- 이 코드는 전형적인 프레임 포인터 사용 예제임. 최적화나 프레임 포인터 생략 등에 따라 실제 함수의 명령어는 달라질 수 있음.

### 18. Function Epilogue — 스택 프레임 정리 (p.43)

> **에필로그** : 함수가 끝날 때 작업 공간을 정리하고 호출자의 프레임으로 복귀하는 명령어 구간

```asm
movl %ebp, %esp
popl %ebp
ret
```

| 단계 | 동작 | 결과 |
|---|---|---|
| `movl %ebp, %esp` | ESP를 현재 프레임 기준점으로 올림 | 지역 변수 영역을 스택에서 해제한 효과 |
| `popl %ebp` | 스택의 saved EBP를 EBP로 복원 | ESP가 4 증가하고 반환 주소를 가리킴 |
| `ret` | 스택의 반환 주소를 EIP로 가져옴 | ESP가 다시 4 증가하고 해당 코드에서 실행 재개 |

- 지역 변수 해제는 그 메모리 바이트를 전부 지운다는 뜻이 아님. **스택 포인터를 이동해 더 이상 현재 프레임 공간으로 사용하지 않는 것**임.
- `popl %ebp`에서 EBP에 들어가는 것은 저장된 값이며, ESP는 pop에 의해 자동으로 이동함.
- **`ret`이 사용하는 것은 현재 ESP가 가리키는 반환 주소 값**임.

```text
정상 반환
저장된 반환 주소 → EIP → 원래 호출 다음 명령

Ret2Libc
변조된 반환 주소(system 주소) → EIP → system의 코드
```
